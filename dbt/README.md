# dbt: core и mart

[Основной README](../README.md) · [Запуск стенда](../infra/README.md) ·
[Краткая карта модели](MODEL_REPORT.md)

Преобразование `stg → core → mart` в Cloudberry: история фильмов и показателей,
дневные снимки и аналитические витрины. Публикация выполняется скриптом
`scripts/build.py` одной транзакцией, без постоянных служебных таблиц dbt.

## Запуск

Предварительно поднимите стенд и создайте таблицы через
`infra/cloudberry/sql/staging.sql`, как описано в [инструкции запуска](../infra/README.md).
Затем примените расширение входного контракта (два nullable-флага полноты
массивов и отдельная таблица полных снимков топа):

```bash
docker compose exec -T --user gpadmin cloudberry bash -lc \
  'source /usr/local/cloudberry-db/cloudberry-env.sh && psql -p 7000 -d etl -v ON_ERROR_STOP=1' \
  < infra/cloudberry/sql/dbt_inputs.sql
```

Рабочая сборка:

```bash
docker compose run --rm --entrypoint python dbt scripts/build.py
# Воспроизводимый расчёт снимков до конкретной UTC-даты:
docker compose run --rm --entrypoint python dbt scripts/build.py --snapshot-end-date 2026-11-10
# Эталонная полная перезапись:
docker compose run --rm --entrypoint python dbt scripts/build.py --full-refresh
```

`build.py` компилирует SQL dbt, блокирует замену staging на время сборки,
загружает seeds, выполняет входные проверки, строит модели в порядке `ref`,
проверяет результат и коммитит **core и mart одной транзакцией**. При ошибке
проверки или SQL откатываются все изменения. Кандидаты — временные таблицы
одного соединения. Постоянных технических таблиц нет. Логи — `dbt/target/logs`.

Обычные `dbt compile`, `dbt test`, `dbt docs generate` доступны. Обычный
`dbt build` также выполняет SQL, но коммитит модели отдельно. Для согласованной
публикации core и mart используйте `scripts/build.py`.
Seed-файлы читает тот же атомарный запуск; отдельный `dbt seed` ему не нужен.

Для отдельной базы передайте `-e CLOUDBERRY_DATABASE=имя` перед сервисом `dbt`.
Источники используют базу профиля; схемы называются ровно `core` и `mart`.

Дополнительные команды из корня репозитория:

```bash
docker compose run --rm dbt compile
docker compose run --rm dbt test
docker compose run --rm dbt docs generate
```

`test` проверяет уже опубликованные отношения; `docs generate` создаёт каталог
в `dbt/target`, который не хранится в git. У сборочного скрипта также есть
`--skip-compile`: он повторно использует `manifest.json` из `DBT_TARGET_PATH`.
Применяйте его только для заранее скомпилированного проекта с теми же vars;
в частности, новая `--snapshot-end-date` без компиляции не изменяет SQL.

## Airflow

В DAG `kinopoisk_movies_daily` и `kinopoisk_movies_replay` задача `build_dbt` запускается после успешной
`load_movies_stg`. `DockerOperator` запускает `python scripts/build.py` в образе
`etl-pet-dbt:1.10.2`, сеть `etl-pet-net`. Перед первым запуском соберите образ
(`docker compose build dbt`) и примените `infra/cloudberry/sql/dbt_inputs.sql`,
как описано выше. Пути bind mounts берутся из `ETL_PROJECT_ROOT` на Docker host.

Проект и профиль монтируются только для чтения. `DBT_TARGET_PATH` и
`DBT_LOG_PATH` указывают на `/tmp/dbt-target` внутри временного контейнера,
поэтому сборка не конфликтует с артефактами ручного запуска. Вывод компиляции,
изменений моделей и проверок попадает в лог задачи Airflow. Пароль передаётся
через `private_environment`. Ошибка скрипта завершает задачу с ошибкой;
настроены один повтор через 5 минут и общий таймаут 30 минут.

Сборка читает весь накопленный staging, без фильтра по батчу DAG.
`--snapshot-end-date` не передаётся: используется текущая UTC-дата запуска dbt.
Так повтор старого интервала не сокращает уже опубликованный горизонт снимков.
Для воспроизводимого исторического среза используйте ручную команду выше.

Проверить только задачу dbt, без повторного обращения к API:

```bash
docker compose exec -T airflow-scheduler airflow tasks test kinopoisk_movies_daily build_dbt 2026-11-11
```

Эта команда выполняет настоящую сборку на текущем staging. Результат конкретного
запуска и число data tests смотрите в логе задачи; интеграционные проверки
выполняются отдельно на одноразовой базе.

## Инкремент

Сравниваются рассчитанное и опубликованное состояния (`EXCEPT` в обе стороны).
Заменяются только разделы, в которых изменились строки: например, вся история
затронутого фильма или полный дневной снимок. Удаления и исчезнувшие группы
также обнаруживаются. Сравнение ключей NULL-безопасное; повтор не перезаписывает
строки моделей. `unique_key` задаёт ключ строки, `partition_keys` — единицу замены.
`--full-refresh` выполняет тот же SELECT и полную перезапись внутри транзакции.

**Ограничение производительности:** сейчас кандидаты вычисляются по всему
накопленному staging. Инкрементальны запись и замена разделов, а не чтение
источника. Это осознанная первая версия без реестра батчей: она обнаруживает
также исправленные и удалённые строки старого батча, которые watermark
`max(updatedAt)` потерял бы. Следующая оптимизация — надёжное определение
изменившихся входных батчей и чтение всей истории только затронутых фильмов.

Версии SCD2 появляются лишь при изменении состояния, включая NULL. Поздние
наблюдения пересчитывают соседние интервалы. Конфликт состояния при одинаковых
`id/source_updated_at` отклоняет всю публикацию до записи core.
Внешние ID фильма обновляются по SCD1. `movie_sk` — детерминированный положительный
60-bit хеш `(movie_id, valid_from UTC)`; коллизия останавливает транзакцию тестом
уникальности. SK жанров/стран равен исходному ID; проверяется диапазон integer.

## Полнота и ограничения источника

- Legacy staging не различает пустой и отсутствующий массив. При NULL-флагах
  сохраняется последний известный непустой набор жанров/стран. Непустой набор
  считается полным; `genres_complete=true` / `countries_complete=true` позволяют
  явно очистить связи пустым набором. Spark передаёт эти флаги через cleaned
  в staging: явный массив (в том числе пустой) без элементов с отсутствующим
  `id` получает `true`; NULL, отсутствующее поле или некорректные элементы —
  `false`. Старые cleaned-батчи без флагов сохраняют прежнее поведение.
- `stg.top250` — отдельный вход: `(snapshot_date, batch_id, position, movie_id,
  observed_at)`. Загружать атомарно весь батч. Публикуются только 250 уникальных
  фильмов на позициях 1–250; выбирается последний полный батч дня. Неполный
  более новый батч не заменяет полный. Если полный ранее опубликованный батч
  перезаписан неполным и другого полного входа дня нет, атомарный запуск
  отклоняет публикацию, сохраняя прежний снимок. Без отдельного загрузчика таблица и
  соответствующая витрина пусты; топ из инкремента фильмов не синтезируется.
  Сравниваются только соседние календарные дни, без переноса через пробелы.
  Агрегаты полноты материализуются перед проверкой: это обходит обнаруженное
  ложное срабатывание HAVING с несколькими COUNT(DISTINCT) на Cloudberry.
- Каталог начинается с даты **получения**, а не `updatedAt`. `built_at` —
  детерминированная UTC-граница конца дня; provenance `batch_id` — первое
  наблюдение фильма. Пустой инкремент не удаляет фильмы из накопленного охвата.
- Денежные агрегаты считаются только для подтверждённых явных кодов. `$`, `€`,
  `₽` и другие символы остаются без маппинга. Новое обозначение требует записи
  seed; пропуск запрещает публикацию. Исторические коды не конвертируются.
- Фильм целиком учитывается в каждой группе жанра/страны; групповые итоги
  пересекаются. Отсутствующая связь получает ключ группы 0; неизвестный год — NULL.
- Недельные дельты — изменение известных состояний на границах ISO-недели;
  отсутствие baseline сохраняет NULL. Последняя неделя может быть неполной.
- После успешной сборки Airflow запускает `publish_clickhouse`: обновление восьми refreshable MV в ClickHouse. Данные читаются напрямую через
  PostgreSQL engine; задача ждёт завершения, без блокировки DWH и переноса строк через Python.
  [Запуск, повторы и границы атомарности](../infra/clickhouse/README.md).

## Проверки

SQL-тесты: ключи, not_null, relationships, интервалы SCD2, конфликты входа,
валютный маппинг, диапазоны оценок/голосов, полнота топа и сверки денежных итогов.
Описания моделей и декларации проверок находятся в `models/core/_models.yml`
и `models/mart/_models.yml`; входы — в `models/sources.yml`, маппинги — в `seeds`.

Интеграционные проверки используют одноразовую Cloudberry-базу:

```bash
# Установить CLOUDBERRY_HOST/PORT/USER/PASSWORD для локального подключения.
RUN_DBT_TESTS=1 uv run pytest tests/integration/test_dbt_models_cloudberry.py -q
```

Проверяются повтор и full-refresh, поздние данные, конфликт времени, настоящий
rollback после записи, удалённые строки и исчезнувшие группы, неизвестные/пустые
массивы, NULL-переходы, SCD1 внешних ID, полные/неполные снимки и движения топа.

Полная настройка окружения тестов — в [tests README](../tests/README.md).
