# dbt: core и mart

[Основной README](../README.md) · [Запуск стенда](../infra/README.md)

Преобразование `stg → core → mart` в Greenplum: история фильмов и показателей,
дневные снимки и аналитические витрины. Публикация выполняется скриптом
`scripts/build.py` одной транзакцией, без постоянных служебных таблиц dbt.

## Запуск

Предварительно поднимите стенд и создайте таблицы через
`infra/greenplum/sql/staging.sql`, как описано в [инструкции запуска](../infra/README.md).
Затем примените расширение входного контракта (два nullable-флага полноты
массивов и отдельная таблица полных снимков топа):

```bash
docker compose exec -T --user gpadmin greenplum bash -lc \
  'source /usr/local/greenplum-db/greenplum_path.sh && psql -X -d etl -v ON_ERROR_STOP=1' \
  < infra/greenplum/sql/dbt_inputs.sql
```

Рабочая сборка:

```bash
docker compose run --rm --entrypoint python dbt scripts/build.py
# Воспроизводимый расчёт снимков до конкретной UTC-даты:
docker compose run --rm --entrypoint python dbt scripts/build.py --snapshot-end-date 2026-11-10
# Эталонная полная перезапись:
docker compose run --rm --entrypoint python dbt scripts/build.py --full-refresh
```

`build.py` компилирует SQL dbt, блокирует замену staging на время сборки,
загружает seeds, выполняет входные проверки, строит модели в порядке `ref`,
проверяет результат и коммитит **core и mart одной транзакцией**. При ошибке
проверки или SQL откатываются все изменения. Кандидаты — временные таблицы
одного соединения. Постоянных технических таблиц нет. Логи — `dbt/target/logs`.

Обычные `dbt compile`, `dbt test`, `dbt docs generate` доступны. Обычный
`dbt build` также выполняет SQL, но коммитит модели отдельно. Для согласованной
публикации core и mart используйте `scripts/build.py`.
Seed-файлы читает тот же атомарный запуск; отдельный `dbt seed` ему не нужен.

Для отдельной базы передайте `-e GREENPLUM_DATABASE=имя` перед сервисом `dbt`.
Источники используют базу профиля; схемы называются ровно `core` и `mart`.

Дополнительные команды из корня репозитория:

```bash
docker compose run --rm dbt compile
docker compose run --rm dbt test
docker compose run --rm dbt docs generate
```

`test` проверяет уже опубликованные отношения; `docs generate` создаёт каталог
в `dbt/target`, который не хранится в git. У сборочного скрипта также есть
`--skip-compile`: он повторно использует `manifest.json` из `DBT_TARGET_PATH`.
Применяйте его только для заранее скомпилированного проекта с теми же vars;
в частности, новая `--snapshot-end-date` без компиляции не изменяет SQL.

## Физическая схема каталога и миграция

`core.fact_movie_catalog_daily` — единственная физически партиционированная
таблица. Хранение использует `RANGE (snapshot_date_sk)` по календарным
месяцам и `DISTRIBUTED BY (movie_id)` с прежним набором колонок.
Сборщик создаёт отсутствующие
месяцы для опубликованных и новых дат, включая backfill. При замене каталога
удаление ограничивается изменившимися месяцами, после чего выполняется
`ANALYZE`. Данные, созданные ранее, не удаляются автоматически: retention не
настроен, пустые месяцы сами не удаляются.

При первом запуске `scripts/build.py` создаёт партиционированную таблицу.
Сборка вычисляет кандидатов и сравнивает строки по всему накопленному staging
и истории. Отсечение партиций сокращает сканирование на этапе удаления
заменяемых дней.

Для уже опубликованной базы Greenplum 7.1.0 приостановите daily и replay в
Airflow и дождитесь завершения текущих задач. Проверьте миграцию на копии базы,
затем в окно обслуживания выполните из корня репозитория:

```bash
docker compose run --rm --no-deps --entrypoint python dbt scripts/migrate_catalog.py --dry-run
docker compose run --rm --no-deps --entrypoint python dbt scripts/migrate_catalog.py --apply
docker compose run --rm --no-deps --entrypoint python dbt scripts/build.py
```

Compose передаёт те же настройки `GREENPLUM_*`, что и сборщику. Для другой
базы укажите `-e GREENPLUM_DATABASE=имя` перед именем сервиса `dbt`.
Проверьте публикацию витрин в ClickHouse и доступность датасетов в Superset,
затем возобновите DAG. Сборщик требует завершённую миграцию каталога для
работы с существующей базой.

По умолчанию CLI выполняет предварительную проверку. Скрипт поддерживает
старый каталог с `DISTRIBUTED RANDOMLY` и обычную таблицу с
`DISTRIBUTED BY (movie_id)`. Применение копирует строки в одной транзакции,
сверяет их количество и содержимое двусторонним `EXCEPT ALL`, затем
заменяет каталог. При ошибке DDL и данные откатываются. Оба режима берут
блокировки staging и `ACCESS EXCLUSIVE` на каталоге. Для применения
нужно место для второй полной копии таблицы и новых партиций. OID
каталога меняется. Предварительная проверка отклоняет зависимости,
неподдерживаемые метаданные, ограничения и индексы.

Для обратного переноса используйте `--reverse --dry-run`, затем
`--reverse --apply` в той же команде Docker Compose. Он восстановит обычную
таблицу с распределением по `movie_id`. После обратного переноса возобновляйте
публикацию со сборщиком предыдущей версии.

## Индексы

Дополнительные продуктовые индексы по результатам замеров не добавлены. Проверка
реального удаления staging batch подтвердила Index Scan по существующим PK
`(batch_id, ...)`; отдельный индекс на `batch_id` дублировал бы их левый префикс.
Семь кандидатов для core и четыре частичных `valid_to IS NULL`/`INCLUDE`
индекса не выбрали Index/Bitmap Scan в проверенных compiled SQL и измерениях,
поэтому оснований включать их в продуктовую схему не получено. Это результат
проверенных запросов и данных, а не утверждение об их бесполезности для любой
нагрузки. При изменении объёма данных или запросов полезность индексов следует
проверять повторно по планам выполнения и стоимости записи.
ClickHouse оставлен без изменений: используются существующие `MergeTree ORDER BY`;
выигрыш его аналитического pruning в этой работе не измерялся.

## Airflow

В DAG `kinopoisk_movies_daily` и `kinopoisk_movies_replay` задача `build_dbt` запускается после успешной
`load_movies_stg`. `DockerOperator` запускает `python scripts/build.py` в образе
`etl-pet-dbt:1.10.2`, сеть `etl-pet-net`. Перед первым запуском соберите образ
(`docker compose build dbt`) и примените `infra/greenplum/sql/dbt_inputs.sql`,
как описано выше. Пути bind mounts берутся из `ETL_PROJECT_ROOT` на Docker host.

Проект и профиль монтируются только для чтения. `DBT_TARGET_PATH` и
`DBT_LOG_PATH` указывают на `/tmp/dbt-target` внутри временного контейнера,
поэтому сборка не конфликтует с артефактами ручного запуска. Вывод компиляции,
изменений моделей и проверок попадает в лог задачи Airflow. Пароль передаётся
через `private_environment`. Ошибка скрипта завершает задачу с ошибкой;
настроены один повтор через 5 минут и общий таймаут 30 минут.

Сборка читает весь накопленный staging, без фильтра по батчу DAG.
`--snapshot-end-date` не передаётся: используется текущая UTC-дата запуска dbt.
Так повтор старого интервала не сокращает уже опубликованный горизонт снимков.
Для воспроизводимого исторического среза используйте ручную команду выше.

Проверить только задачу dbt, без повторного обращения к API:

```bash
docker compose exec -T airflow-scheduler airflow tasks test kinopoisk_movies_daily build_dbt 2026-11-11
```

Эта команда выполняет настоящую сборку на текущем staging. Результат конкретного
запуска и число data tests смотрите в логе задачи; интеграционные проверки
выполняются отдельно на одноразовой базе.

## Модели

| Группа | Модели | Гранулярность |
| --- | --- | --- |
| Справочники | `dim_currency`, `dim_market`, `dim_genre`, `dim_country`, `dim_date` | Валюта, рынок, жанр, страна, UTC-дата |
| Версии фильма | `dim_movie` | Фильм × начало версии SCD2 |
| Мосты | `bridge_movie_genre`, `bridge_movie_country` | Версия фильма × жанр/страна |
| История | `fact_budget_history`, `fact_box_office_history`, `fact_movie_scores_history` | Фильм × начало состояния; сборы дополнительно × рынок |
| Снимки | `fact_movie_catalog_daily`, `fact_top250_daily` | UTC-день × фильм; топ — день × позиция |
| Текущие представления | `v_movie_current`, `v_budget_current`, `v_box_office_current`, `v_movie_scores_current` | Открытые версии, `valid_to IS NULL` |
| Каталог | `mart_catalog_year_genre`, `mart_catalog_year_country` | День × год производства × жанр/страна |
| Оценки | `mart_movie_scores_current`, `mart_movie_popularity_weekly` | Фильм; ISO-неделя × фильм |
| Деньги | `mart_budget_current_by_currency`, `mart_box_office_current_by_market_currency`, `mart_budget_vs_box_office` | Валюта; рынок × валюта; фильм × рынок |
| Топ | `mart_top250_daily_changes` | День × фильм из объединения соседних полных снимков |

Всего **25 моделей: 13 таблиц core, 4 текущих view, 8 таблиц mart**.
Все 21 таблица настроены как `incremental`, стратегия `reconcile`.

В витринах на уровне фильма доступны название, альтернативное название, год
производства, длительность, возрастной рейтинг и MPAA. Текущие оценки и
сопоставление бюджета со сборами используют текущую версию фильма. Недельная
популярность использует версию на конец ISO-недели или последнего доступного
UTC-дня для неполной недели. Топ-250 использует версию на конец дня снимка.
Если на эту дату версия фильма отсутствует, атрибуты равны NULL.

Витрины каталога содержат названия жанра или страны, финансовые витрины в
разрезе рынка содержат его код и название. В сопоставлении бюджета и сборов
также доступны отдельные коды обеих валют.

## Распределение core в Greenplum

Атомарный сборщик `scripts/build.py` явно задаёт политику при создании таблиц:

| Таблицы | Политика |
| --- | --- |
| `dim_movie`, `fact_budget_history`, `fact_box_office_history`, `fact_movie_scores_history`, `fact_movie_catalog_daily`, `fact_top250_daily` | `DISTRIBUTED BY (movie_id)` |
| `bridge_movie_genre`, `bridge_movie_country` | `DISTRIBUTED BY (movie_sk)` |
| `dim_date`, `dim_genre`, `dim_country`, `dim_currency`, `dim_market` | `DISTRIBUTED REPLICATED` |
| Seeds `currency_mapping`, `market_mapping` | `DISTRIBUTED REPLICATED` |

Для существующих таблиц сборщик сверяет `gp_distribution_policy` и выполняет
`ALTER TABLE ... SET DISTRIBUTED ...` только при несовпадении, затем `ANALYZE`.
Миграция распределения входит в транзакцию публикации: ошибка откатывает данные
и распределение. Изменение физической схемы каталога выполняется отдельно — см.
раздел «Физическая схема каталога и миграция» выше. Перераспределение при
изменении политики требует блокировок; следующие запуски не повторяют его.
Обычный `dbt build` не применяет эти политики: используйте `scripts/build.py`.

Мосты соединяются с `dim_movie` по `movie_sk`, поэтому их распределение
не гарантирует локальный join с `dim_movie`, распределённой по `movie_id`.
`partition_keys` остаётся единицей логической инкрементальной замены строк;
физические партиции используются только у дневного каталога. Политики `mart`
не меняются.

## Инкремент

Сравниваются рассчитанное и опубликованное состояния (`EXCEPT` в обе стороны).
Заменяются только разделы, в которых изменились строки: например, вся история
затронутого фильма или полный дневной снимок. Удаления и исчезнувшие группы
также обнаруживаются. Сравнение ключей NULL-безопасное; повтор не перезаписывает
строки моделей. `unique_key` задаёт ключ строки, `partition_keys` — единицу замены.
`--full-refresh` выполняет тот же SELECT и полную перезапись внутри транзакции.

**Ограничение производительности:** сейчас кандидаты вычисляются по всему
накопленному staging. Инкрементальны запись и замена разделов, а не чтение
источника. Это осознанная первая версия без реестра батчей: она обнаруживает
также исправленные и удалённые строки старого батча, которые watermark
`max(updatedAt)` потерял бы. Следующая оптимизация — надёжное определение
изменившихся входных батчей и чтение всей истории только затронутых фильмов.

Версии SCD2 появляются лишь при изменении состояния, включая NULL. Поздние
наблюдения пересчитывают соседние интервалы. Конфликт состояния при одинаковых
`id/source_updated_at` отклоняет всю публикацию до записи core.
Внешние ID фильма обновляются по SCD1. `movie_sk` — детерминированный положительный
60-bit хеш `(movie_id, valid_from UTC)`; коллизия останавливает транзакцию тестом
уникальности. SK жанров/стран равен исходному ID; проверяется диапазон integer.

## Полнота и ограничения источника

- Legacy staging не различает пустой и отсутствующий массив. При NULL-флагах
  сохраняется последний известный непустой набор жанров/стран. Непустой набор
  считается полным; `genres_complete=true` / `countries_complete=true` позволяют
  явно очистить связи пустым набором. Spark передаёт эти флаги через cleaned
  в staging: явный массив (в том числе пустой) без элементов с отсутствующим
  `id` получает `true`; NULL, отсутствующее поле или некорректные элементы —
  `false`. Старые cleaned-батчи без флагов сохраняют прежнее поведение.
- `stg.top250` — отдельный вход: `(snapshot_date, batch_id, position, movie_id,
  observed_at)`. Загружать атомарно весь батч. Публикуются только 250 уникальных
  фильмов на позициях 1–250; выбирается последний полный батч дня. Неполный
  более новый батч не заменяет полный. Если полный ранее опубликованный батч
  перезаписан неполным и другого полного входа дня нет, атомарный запуск
  отклоняет публикацию, сохраняя прежний снимок. Без отдельного загрузчика таблица и
  соответствующая витрина пусты; топ из инкремента фильмов не синтезируется.
  Сравниваются только соседние календарные дни, без переноса через пробелы.
  Агрегаты полноты вычисляются перед сравнением.
- Каталог начинается с даты **получения**, а не `updatedAt`. `built_at` —
  детерминированная UTC-граница конца дня; provenance `batch_id` — первое
  наблюдение фильма. Пустой инкремент не удаляет фильмы из накопленного охвата.
- Денежные агрегаты считаются только для подтверждённых явных кодов. `$`, `€`,
  `₽` и другие символы остаются без маппинга. Новое обозначение требует записи
  seed; пропуск запрещает публикацию. Исторические коды не конвертируются.
- Фильм целиком учитывается в каждой группе жанра/страны; групповые итоги
  пересекаются. Отсутствующая связь получает ключ группы 0; неизвестный год — NULL.
- Недельные дельты — изменение известных состояний на границах ISO-недели;
  отсутствие baseline сохраняет NULL. Последняя неделя может быть неполной.
- После успешной сборки Airflow запускает `publish_clickhouse`: обновление восьми refreshable MV в ClickHouse. Данные читаются напрямую через
  PostgreSQL engine; задача ждёт завершения, без блокировки DWH и переноса строк через Python.
  [Запуск, повторы и границы атомарности](../infra/clickhouse/README.md).

## Проверки

SQL-тесты: ключи, not_null, relationships, интервалы SCD2, конфликты входа,
валютный маппинг, диапазоны оценок/голосов, полнота топа и сверки денежных итогов.
Описания моделей и декларации проверок находятся в `models/core/_models.yml`
и `models/mart/_models.yml`; входы — в `models/sources.yml`, маппинги — в `seeds`.

Интеграционные проверки используют одноразовую Greenplum-базу:

```bash
# Установить GREENPLUM_HOST/PORT/USER/PASSWORD для локального подключения.
RUN_DBT_TESTS=1 uv run pytest tests/integration/test_dbt_models_greenplum.py -q
```

Проверяются повтор и full-refresh, поздние данные, конфликт времени, настоящий
rollback после записи, удалённые строки и исчезнувшие группы, неизвестные/пустые
массивы, NULL-переходы, SCD1 внешних ID, полные/неполные снимки и движения топа.

Полная настройка окружения тестов — в [tests README](../tests/README.md).

Интеграционные тесты проверяют политики 15 таблиц core с учётом seeds,
обновление с прежнего распределения, отсутствие повторного перераспределения,
отсечение месячных партиций в GPORCA и сохранность данных при прямой и обратной
миграциях каталога и при ошибке.

## Проверка объёмов опубликованных данных

Объёмы зависят от сохранённых батчей и горизонта сборки:

```bash
docker compose run --rm dbt test
docker compose exec -T --user gpadmin greenplum bash -lc \
  'source /usr/local/greenplum-db/greenplum_path.sh && psql -X -d etl -v ON_ERROR_STOP=1' <<'SQL'
SELECT count(*) AS movie_versions FROM core.dim_movie;
SELECT count(*) AS current_movies FROM core.v_movie_current;
SELECT min(snapshot_date_sk), max(snapshot_date_sk), count(*)
FROM core.fact_movie_catalog_daily;
SELECT count(*) AS top250_rows FROM core.fact_top250_daily;
SQL
```
